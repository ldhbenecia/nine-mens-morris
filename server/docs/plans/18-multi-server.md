# 18. 서버 여러 대로 띄우기 — Redis 공유 상태와 pub/sub

결정 자체는 [ADR-17](07-architecture-decision.md) 에 있다. 이 문서는 **왜 이렇게 됐고 각 장치가 무엇을 막는지**를 설명한다.

---

## 1. 출발점: 코드에 "서버는 한 대" 가 박혀 있었다

```
플레이어 A ─┐
            ├─ 서버 1 [방 목록, 판, 방 락, 소켓 목록]  ← 전부 JVM 메모리
플레이어 B ─┘
```

이 서버가 죽거나 배포로 재시작되면 진행 중인 판이 전부 사라진다(실제로 "방을 찾을 수 없습니다").
그래서 서버를 두 대로 늘리면 로드밸런서는 A 를 서버 1 에, B 를 서버 2 에 보낼 수 있다.

```
플레이어 A ── 서버 1 [7번 방 판]
플레이어 B ── 서버 2 [7번 방 모름]   ← B 가 두면 "방을 찾을 수 없습니다"
```

두 대가 맞게 돌려면 아래 다섯 가지가 모두 필요했다.

| # | 한 대일 때 | 두 대에서 깨지는 것 | 바꾼 것 |
| --- | --- | --- | --- |
| ① | 판 상태가 메모리 | 다른 서버가 모름 | Redis 에 둠 (`RoomStore`) |
| ② | `synchronized` 방 락 | 다른 서버를 못 막음 | Redis 락 + 버전 확인 |
| ③ | 여러 값을 따로 고침 | 중간에 죽으면 어긋남 | Lua 로 한 번에 |
| ④ | `SimpleBroker` 가 자기 세션에만 보냄 | 다른 서버에 붙은 상대가 못 받음 | Redis pub/sub, 방마다 채널 |
| ⑤ | 재접속 여부를 그 서버 세션 표로 판단 | 다른 서버로 다시 붙은 사람을 기권 처리 | 접속 여부를 Redis 에 (`ClusterPresence`) |

---

## 2. 판 상태를 Redis 에 (공유 저장소)

판을 어느 서버도 들고 있지 않는다. 수를 둘 때마다 **Redis 에서 읽고 → 규칙을 적용하고 → 다시 쓴다.**

- 서버가 상태를 갖지 않으므로(stateless) 아무 서버나 죽어도 된다. 클라이언트는 다른 서버로 다시 붙어 그대로 둔다
- 대가는 수마다 Redis 왕복(약 1ms). 이 게임은 한 방에 몇 초에 한 수라 체감되지 않는다
- 변경 하나는 왕복 3번: 락(`SET NX PX`) → 읽기(`HGETALL`) → 쓰기·색인 갱신·락 해제를 한 Lua 로
- 거절된 수·동기화처럼 바뀐 게 없으면 다시 쓰지 않고 락만 푼다. revision 과 활동 시각도 그대로라
  헛된 요청이 이벤트 순서 판단이나 유휴 정리에 끼어들지 않는다

저장 형식은 `RoomSnapshot`(JSON). 판 안에는 화면에 안 보이는 상태(3회 반복 기록, 무승부 제안 횟수)까지 들어 있어야
되살린 판의 규칙이 같다 (`GameSnapshotTest`).

| 키 | 내용 |
| --- | --- |
| `room:{id}` | 해시 `{ json, ver }` |
| `rooms` | 방 id 집합 (로비 목록) |
| `rooms:turn-deadline` | 진행 중인 방의 턴 마감 시각 (ZSET) — 턴 만료 후보 |
| `rooms:activity` | 마지막 활동 시각 (ZSET) — 유휴 정리 후보 |
| `lock:room:{id}` | 방 락 |

모듈: 저장 기술은 `morris-storage` 의 `RoomStore` 가 맡고 스냅샷(데이터)만 다룬다.
`morris-api` 의 `RedisRoomRegistry` 가 스냅샷과 도메인 객체 `Room` 을 오간다. 저장소는 규칙을 모른다.

## 3. 방 락 — 왜 락에 버전 확인까지

락이 없으면:

```
서버 1: 7번 방 읽음(흑 차례) → 흑 0번에 둠 → 저장
서버 2: 7번 방 읽음(흑 차례) → 흑 5번에 둠 → 저장   ← 서버 1 의 수를 덮어씀
```

`SET lock:room:7 <토큰> NX PX 5000` — "아무도 안 잡았을 때만 잡고, 5초 뒤 자동으로 풀림".

| 장치 | 막는 것 |
| --- | --- |
| **5초 임대** | 락을 쥔 서버가 죽으면 그 방이 영원히 잠김 |
| **토큰** | 내 임대가 끝나 다른 서버가 잡은 락을 내가 지움. 해제는 토큰이 같을 때만(Lua) |
| **쓰기 때 버전 확인** | GC 등으로 5초 넘게 멈췄다 깨어난 서버의 늦은 쓰기. 락만으로는 못 막아서, 읽을 때의 버전과 같을 때만 쓰기 성공(compare-and-swap) |

검증: 같은 Redis 를 보는 저장소 둘(= 서버 둘)이 같은 방에 동시에 20수를 두려 하면 정확히 하나만 받아들여진다
(`RoomRegistryContract.동시_변경은_하나씩`).

---

## 4. Lua — 명령 여러 개를 하나로

저장 한 번에 방 데이터·방 목록·턴 마감 색인·활동 색인 넷을 같이 고친다.
따로 보내면 중간에 서버가 죽었을 때 "방은 있는데 목록에 없음", "지운 방이 마감 색인에 남음" 이 생긴다.
Redis 는 Lua 스크립트를 중간에 끊지 않고 실행하므로 넷이 같이 성공하거나 같이 실패한다.

Lua 가 여러 키를 건드리므로 **Redis Cluster(샤딩)가 아니라 단일 마스터 + Sentinel** 을 전제로 한다.

## 5. 방 이벤트 전파 — pub/sub

### 문제

STOMP 의 `SimpleBroker` 는 **자기 서버에 붙은 소켓만** 안다.

```
A 가 서버 1 에서 둠 → 서버 1 브로커 "7번 방 구독자에게" → A 만 받음. 서버 2 의 B 는 못 받음
```

### pub/sub 이란

Redis 의 방송 기능. 채널에 발행(PUBLISH)하면 **그 순간 그 채널을 구독(SUBSCRIBE) 중인 연결 모두**가 받는다.
라디오와 같다. 저장하지 않는다.

### 방마다 채널, 구독자가 있는 서버만 구독

```
7번 방 두 사람이 서버 1, 2 에 붙음 → 서버 1, 2 만 morris:room:7 을 구독

A 가 둠 → 서버 1 이 morris:room:7 에 PUBLISH
       → 서버 1, 2 가 받음 → 각자 자기 브로커로 → A, B
       → 서버 3~8 은 구독하지 않아 아무것도 안 받음
```

- 이 서버에 그 방의 **첫 구독자가 생기면** 채널을 구독하고 **마지막이 떠나면** 해제한다 (서버별 참조 카운트)
- 채널 하나로 모든 서버에 뿌리면 서버 8대일 때 두 사람의 판이 나머지 6대에도 가서 버려진다. 그래서 나눴다
- 보낸 서버도 채널을 거쳐 받는다. 자기 브로커로 직접 보내면 두 번 간다
- **로비**는 방 생성·입장·퇴장 때만 오는 드문 신호라 모든 서버가 늘 구독한다
- **개인 큐**(`/user/queue/*`, 거절 사유·sync 응답)는 그 요청을 보낸 세션이 그 서버에 있으므로 Redis 를 거치지 않는다

검증: `ClusterBroadcasterTest` — 구독자 없는 서버는 안 받음, 둘 다 받음, 마지막 세션이 떠나면 해제, 로비는 모두.

### 유실은 어떻게 메우나

pub/sub 은 전달을 보장하지 않는다. 그 순간 죽어 있거나 막 구독하는 중인 서버는 놓친다.
하지만 게임 메시지는 "최신 판 상태" 라 중간 이벤트를 놓쳐도 마지막 상태만 받으면 화면이 맞고,
클라이언트는 **구독 직후와 재접속 때 `sync` 로 판 전체를 받는다.**

### 순서가 뒤바뀌면 — revision

락을 놓은 뒤 전송하므로 서버 둘의 이벤트가 뒤바뀌어 도착할 수 있다
(서버 1 이 보내기 직전에 서버 2 가 다음 수를 처리해 먼저 보냄).
방이 바뀔 때마다 오르는 `revision` 을 판 상태에 싣고, **클라이언트는 지금보다 오래된 판을 버린다.**

## 6. RabbitMQ 를 붙이지 않은 이유

### RabbitMQ STOMP 브로커 릴레이였다면

스프링 `enableStompBrokerRelay()`. 앱 서버는 STOMP 프레임을 RabbitMQ 로 넘기는 중계기가 되고 구독·배달은 RabbitMQ 가 한다.

```
브라우저 A ─WS─ 서버 1 ─TCP(세션당 1개)─┐
                                        ├─ RabbitMQ (구독 목록·큐)
브라우저 B ─WS─ 서버 2 ─TCP(세션당 1개)─┘
```

### 비교

| | RabbitMQ 릴레이 | Redis pub/sub (지금) |
| --- | --- | --- |
| 추가 인프라 | RabbitMQ 클러스터 (Erlang, 쿼럼 큐 운영) | 없음 (판 상태 때문에 이미 Redis 있음) |
| 구독 관리 | RabbitMQ | 각 서버의 SimpleBroker |
| 연결 수 | **브라우저 세션당 1개** | 서버당 구독 연결 1개 |
| 전달 보장 | 있음 (ack, 큐 보관) | 없음 |
| 메시지가 가는 곳 | 구독자가 있는 곳만 | 구독자가 있는 서버만 (방마다 채널) |
| 다른 서버 사용자에게 개인 메시지 | 됨 | 안 됨 (지금은 필요 없음) |
| 앱 서버가 죽을 때 | 재접속 + sync | 재접속 + sync |

### 결정적인 이유

**WebSocket 은 앱 서버에서 끝난다.** 앱 서버가 죽으면 RabbitMQ 가 메시지를 큐에 쥐고 있어도 브라우저에 건네줄 서버가 없다.
결국 두 방식 모두 "다른 서버로 다시 붙어 sync 로 판 전체를 받는다" 로 복구한다.
전달 보장이 이 게임의 실제 장애(앱 서버 다운)에서 더해 주는 것이 없다.

### RabbitMQ 를 다시 검토할 때

- 오프라인 사용자에게 쌓아 둬야 하는 메시지 (대국 신청·친구 초대 알림)
- 다른 서버에 붙은 특정 사용자에게 보내기 (귓속말)
- 우선순위·재시도·지연 전달 같은 라우팅이 필요할 때

## 7. 재접속 유예 — 서버 전체 기준 접속 여부

이미 "끊기고 10초 안에 안 돌아오면 기권" 로직이 있었다. 문제는 "돌아왔나" 를 **그 서버의 세션 표만 보고** 판단한 것.
A 가 서버 1 에서 끊기고 서버 2 로 다시 붙으면 서버 1 은 "안 돌아왔다" 고 보고 잘못 기권 처리한다.

| 키 | 내용 |
| --- | --- |
| `presence:{roomId}:{userId}` | 그 방에 붙은 세션 집합 `{서버id:세션id}` |
| `instance:{서버id}` | 서버 생존 키. TTL 15초, 5초마다 갱신. 쿠버네티스에서는 서버id = 파드 이름 |

**죽은 서버는 해제 이벤트를 못 보내 그 세션이 집합에 남는다.** 생존 키가 없는 서버의 세션은 없는 것으로 본다.
끝내 아무도 돌아오지 않으면 턴 제한 시간(ADR-16)이 판을 끝낸다.

검증: `ClusterPresenceTest` — 다른 서버로 다시 붙음, 다른 방 세션, 죽은 서버, 하나라도 살아 있으면.

---

## 8. 스케줄러 — 서버마다 돌아도 두 번 처리하지 않는다

턴 만료·유휴 방 정리는 모든 서버에서 돈다. 리더 선출을 따로 두지 않았다.

1. 후보를 락 없이 고른다 (ZSET 에서 마감이 지난 방)
2. 방 락을 잡고 **다시 확인한다**
3. 두 서버가 같은 방을 골라도 두 번째 서버는 락 안에서 "이미 끝난 판" 을 보고 아무것도 안 한다

DB 의 유휴 게스트 정리는 같은 조건의 `DELETE` 라 여러 서버가 돌아도 결과가 같다.

## 9. "클러스터" 라는 말

| 용어 | 뜻 | 여기서 |
| --- | --- | --- |
| 앱 서버 여러 대 | 로드밸런서 뒤 스프링 서버 여러 대 | **이 작업의 목표**. `Cluster*` 클래스 이름은 이 뜻 |
| Redis Sentinel | 주 1 + 복제본, 주가 죽으면 자동 승격 | 운영의 Redis 이중화 |
| Redis Cluster | 데이터를 여러 Redis 로 나눠 저장(샤딩) | 쓰지 않음. 데이터가 작고 Lua 가 여러 키를 건드림 |

## 10. 검증

`MultiServerGameTest` — 한 JVM 에서 **스프링 앱 두 개를 실제로 띄워** 같은 MySQL·Redis 컨테이너를 보게 함.

| 시나리오 | 확인한 것 |
| --- | --- |
| 서로 다른 서버의 두 사람이 한 판 | 방은 A 에서 만들고 입장은 B. 각자 자기 서버에서 둔 수가 상대 서버로 도착. revision 이 오름. B 쪽 기권이 A 쪽에 승리로 도착 |
| 판 도중 서버 하나가 내려감 | B 를 정상 종료(배포 상황)하는 동안 참가자가 A 로 다시 붙어 `sync` 로 같은 판을 받음. 이어서 둠. 재접속 유예(10초)가 지나도 기권 처리되지 않음 |

나머지는 단위·통합 테스트로 나눠 고정했다.

| 테스트 | 대상 |
| --- | --- |
| `GameSnapshotTest` | 저장했다 되살린 판의 규칙이 같음 (3회 반복·제안 횟수) |
| `RoomRegistryContract` (메모리·Redis) | 서버 둘이 같은 방에 동시에 20수 → 하나만 받아들여짐 외 7건 |
| `ClusterBroadcasterTest` | 그 방 구독자가 없는 서버는 이벤트를 받지 않음 |
| `ClusterPresenceTest` | 다른 서버로 다시 붙음·죽은 서버의 세션 |
| `VisitorIssueLimiterTest` | 서버가 달라도 같은 IP 발급을 합쳐서 셈 |

## 11. 감수하는 것

- **Redis 가 판 상태의 유일한 원본**이다. 운영은 Sentinel 로 이중화하고, 끊기면 readiness 가 트래픽을 뺀다
- 비동기 복제라 장애 조치 직전의 마지막 수 하나는 사라질 수 있다. 판은 직전 상태로 이어진다
- 수마다 Redis 왕복이 생긴다 (방 하나에 몇 초에 한 수라 문제되지 않음)
