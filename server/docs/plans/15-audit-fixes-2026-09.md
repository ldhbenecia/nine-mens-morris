## 1. 게임 종료 경로 4개 중 3개가 결과를 기록하지 않음

커밋 `1b18008`

### 문제

게임이 끝나는 경로는 네 개인데 정산하는 경로는 하나뿐이었다.

| 경로 | 정산 | 방 정리 |
| --- | --- | --- |
| 수를 둬서 승부가 남 | O | X (방이 영구히 남음) |
| 소켓 끊김 + 유예 만료 | O | X |
| REST 로 나가기 | **X** | O |
| 30분 유휴 정리 | **X** | O |

- `RoomService.leave` 에 진행 중 검사가 없었다. 게스트면 `leaveGuest()` 가 `game = null` 로
  판을 지우고, 방장이면 `rooms.remove()` 가 방을 지웠다. 둘 다 `settle()` 을 타지 않았다
- `RoomRegistry.purgeIdleRooms` 는 `lastActivityAt` 만 보고 `isPlaying()` 검사 없이 삭제했다
- 정산이 끝난 뒤에도 `guestId` 가 남아 방이 로비에 계속 떴다

### 무엇을 야기하는가

**지고 있을 때 나가기를 누르는 쪽이 이득이다.** 패배도, MMR 하락도, `matches` 행도 남지 않는다.
소켓을 끊는 경로는 기권 처리를 하도록 일부러 만들어 놨는데, 그 바로 옆 REST 문이 열려 있어서
1차 조사에서 막았다고 생각한 어뷰징이 그대로 살아 있었다.

유휴 정리 쪽은 더 조용하다. 양쪽이 방치한 판이 30분 뒤 아무 기록 없이 사라지고,
로그에는 건수만 남아서 "내 판이 사라졌다"는 제보가 와도 볼 근거가 없다.

정산 후 방이 남는 것은 그 자체로도 문제지만, `isPlaying()` 이 false 이고 `guestId` 가 남아 있으니
**방장이 소켓도 없는 상대와 새 게임을 시작할 수 있었다.** 그 판은 영원히 끝나지 않는다.

### 어떻게 고쳤는가

네 경로가 공유하는 단일 종료 루틴 `GameService.exit(roomId, userId, cause)` 를 만들고
끊김·나가기가 모두 그것을 타게 했다. 유휴 정리는 `settleAbandoned` 로 같은 정산 경로를 쓴다.

- `RoomService.leave` 를 없애고 `GameService.leave` 로 옮겼다
- `RoomRegistry` 는 `findIdle(threshold)` 로 대상만 고르고, 정리 판단과 정산은 `GameService` 가 한다
- 스케줄과 브로드캐스트는 `IdleRoomPurger` 가 맡는다
- 진행 중이던 방이 유휴로 정리될 때는 `EndReason.ABANDONED` 무승부로 기록한다
- 정산 후 `removeFromRoom` 으로 방을 비운다
- `leaveGuest()` 가 **끝난 판까지** 지우던 것을 고쳐 판 기록은 남기고, 새 참가자가 들어올 때 비운다
- 나가기 브로드캐스트는 서비스가 이벤트를 돌려줬을 때만 보낸다

### 왜 그렇게 고쳤는가

경로별로 정산을 따로 구현했기 때문에 세 개가 빠졌다.
같은 실수가 다시 나지 않으려면 **정산을 건너뛸 수 있는 경로가 구조적으로 없어야 한다.**
그래서 분기를 늘리는 대신 경로를 하나로 모았다.

방치를 무승부로 한 이유는 어느 한쪽의 잘못이 아니기 때문이다.
승패를 주면 "상대가 나가기만 기다리는" 또 다른 어뷰징이 생긴다.
그렇다고 기록을 남기지 않으면 원장이 불완전해져서 `users` 의 집계값을 재계산할 수 없다.

`RoomRegistry` 에서 정리를 빼낸 이유는 그곳이 저장소이고 `MatchResultService` 를 알아서는
안 되기 때문이다. 스케줄까지 `GameService` 에 두면 서비스가 `SimpMessagingTemplate` 을
알아야 해서, 브로드캐스트만 하는 얇은 컴포넌트를 바깥에 뒀다.

`leaveGuest()` 가 끝난 판을 지우면 안 되는 이유는, 남은 사람이 결과 화면에서 새로고침했을 때
승패를 잃기 때문이다.

### 기대 효과

- 어떤 방식으로 판을 떠나도 결과가 남는다. 나가기로 MMR 하락을 피할 수 없다
- 로비에 시체 방이 쌓이지 않는다
- 방치된 판도 원장에 남아 집계를 재계산할 수 있다
- 방에 속하지 않은 사람이 남의 방에 `PLAYER_LEFT` 를 꽂을 수 없다

### 동작 검증

고치기 전 실측

```
게임 PLAYING 상태에서 게스트가 DELETE /api/v1/rooms/{id}/players/me
→ 204, 방은 playing:false / guestId:null
→ 호스트가 받은 이벤트: PLAYER_LEFT 뿐
→ matches 2건 → 2건 (변화 없음), 승패·MMR 변화 없음
```

고친 뒤 단위 테스트 8개 추가 (전부 통과)

- 게임 중 나가면 기권 처리되고 전적이 기록된다
- 정산이 끝나면 방이 대기 상태로 돌아간다
- 방에 속하지 않은 사람이 나가면 알릴 것이 없다
- 없는 방에서 나가도 오류가 아니다
- 대기 중에 나가면 정산 없이 퇴장만 알린다
- 진행 중이던 방은 무승부로 기록하고 지운다
- 시작 전 방은 조용히 지운다
- 최근까지 쓰인 방은 건드리지 않는다

유휴 기준을 `game.room.idle-timeout` 설정으로 뺐다. 30분이 코드에 박혀 있으면 검증할 수 없다.

## 2. 여분 탭이 열려 있으면 끊김 정산이 예약조차 되지 않음

커밋 `13a4c8d`

### 문제

```java
if (sessions.hasActiveSession(userId)) {
    return;                 // 예약조차 하지 않음
}
```

`hasActiveSession` 은 **사용자 단위**라 "같은 방에 다시 붙었다"와
"무관한 탭이 하나 떠 있다"를 구분할 수 없었다.

추가로 `SessionTracker.add` 가 `computeIfAbsent` 밖에서 집합을 고쳤다.

```java
sessionsByUser.computeIfAbsent(userId, k -> newKeySet()).add(sessionId);
```

### 무엇을 야기하는가

로비를 탭 A 에 띄워 둔 채 탭 B 에서 게임하다 탭 B 만 닫으면 정산이 **영구히** 돌지 않는다.
턴 제한 시간이 코드에 전혀 없으므로 상대는 멈춘 판을 계속 보게 되고,
30분 뒤 유휴 정리가 (위 1번을 고치기 전에는) 기록 없이 방을 지운다.

`add` 의 경쟁 조건은 반대 방향으로 위험하다. 접속과 해제가 다른 스레드에서 겹치면
방금 추가된 세션이 맵에서 빠져 `hasActiveSession` 이 영구히 false 가 되고,
**접속 중인 사람이 기권 처리된다.** 이 두 이벤트는 화면 이동 때마다 다른 스레드에서 발생한다.

### 어떻게 고쳤는가

세션이 어느 방을 보고 있는지까지 추적한다.

- `SessionSubscribeEvent` 에서 `/topic/rooms/{id}` 구독을 잡아 세션↔방을 묶는다
- `isWatching(userId, roomId)` 로 "그 방에 붙어 있는 세션" 만 본다
- 끊김 시 항상 유예 작업을 예약하고, 만료 시점에 `isWatching` 으로 판단한다
- `handleDisconnect(userId, roomId)` 로 방을 명시해서 받는다
- `add` / `remove` 의 집합 변경을 `compute` 안에서 끝낸다

### 왜 그렇게 고쳤는가

방 토픽 구독이 "이 세션이 그 방을 보고 있다"는 **유일한 신호**다.
별도의 "방 입장 핑" 같은 것을 새로 만들 수도 있지만, 이미 존재하는 신호를 쓰는 편이
클라이언트 변경이 필요 없고 어긋날 여지도 없다.

`handleDisconnect` 가 `findByPlayer` 로 방을 찾던 것도 같이 바꿨다.
한 사용자가 여러 방에 속할 수 있고 `findByPlayer` 는 `ConcurrentHashMap` 버킷 순서를 따르므로
사실상 임의의 방이 뽑혔다. 유휴 방이 뽑히면 진행 중인 판이 정산되지 않는다.
구독 정보가 있으면 어느 방인지 정확히 알 수 있으므로 추측할 필요가 없어졌다.

### 기대 효과

- 탭을 여러 개 열어 두는 평범한 사용 패턴에서도 정산이 제대로 돈다
- 같은 방에 세션이 겹치는 순간(새로고침·화면 이동)에는 여전히 유예가 동작한다
- 접속 중인 사람이 기권 처리되는 일이 없다
- 한 사용자가 여러 방에 있어도 정확한 방이 정리된다

### 동작 검증

실서버 3개 시나리오 (각 13초 대기)

| 시나리오 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 로비 탭 유지 + 게임 탭만 닫기 | 이벤트 없음, 방 `playing:true`, 전적 불변 | `OPPONENT_DISCONNECTED(FINISHED)`, 1001 이 2승→3승 |
| 같은 방 세션 2개 중 하나만 닫기 | — | 이벤트 없음, 방 `playing:true` (유예 정상) |
| 남은 세션까지 닫기 | — | `OPPONENT_DISCONNECTED(FINISHED)`, 1001 이 3승→4승 |

경쟁 조건은 접속·해제를 동시에 실행하는 500회 반복 테스트로 고정했다.

## 3. 검증 실패가 401 "로그인이 필요합니다" 로 둔갑

커밋 `ada5ffe`

### 문제

빈 제목으로 방을 만들면 400 이 아니라 **401** 이 돌아왔다.
깨진 JSON, `/rooms/abc`, `rankings?limit=-1` 도 모두 401 이었다.

서버 로그에는 `MethodArgumentNotValidException` 이 400 으로 해결됐다고 찍히는데,
그 뒤 `/error` 로 포워딩되면서 `anyRequest().denyAll()` 에 걸려 인증 실패로 덮였다.

더불어 실패 응답 스키마가 세 종류였다.

| 상황 | 응답 |
| --- | --- |
| `CustomException` | `{status, name, message}` |
| 인증 실패 | `{code, message}` |
| 검증 실패 | Spring 기본 형태 |

그리고 STOMP 에서 던진 `CustomException` 은 클라이언트에 **도달하지 않았다.**
`@RestControllerAdvice` 는 메시징에 적용되지 않고 `@MessageExceptionHandler` 도 없었다.

### 무엇을 야기하는가

**프론트가 401 을 보고 사용자를 로그아웃시킨다.** 제목을 비워 둔 것 때문에 로그인이 풀린다.

스키마가 세 종류라는 것은 클라이언트가 세 가지를 따로 다뤄야 한다는 뜻이고,
실제로는 다루지 않으므로 대부분의 실패가 먹통 클릭이 된다.

STOMP 쪽은 더 나쁘다. 방장이 아닌 사람이 "게임 시작"을 눌러도, 혼자 있을 때 시작해도,
없는 방에 명령을 보내도 **화면에 아무 반응이 없다.** 그러면서 서버 로그에는
평범한 오조작마다 ERROR 스택트레이스가 쌓인다.

`@Payload` 에 `@Valid` 가 없어 좌표 검증이 전혀 걸리지 않는 문제도 함께 있었다.
`PlaceRequest(int to)` 는 필드가 빠진 요청을 조용히 `to = 0` 으로 만들어
**"0번 지점 착수"라는 합법적인 수로 처리했다.**

### 어떻게 고쳤는가

- `SecurityConfig` 에서 `DispatcherType.ERROR` 를 먼저 `permitAll`
- `CustomExceptionHandler` 가 검증 실패·파싱 오류·예상 못한 예외까지 처리.
  검증 실패는 어느 필드가 왜 틀렸는지 함께 내려준다
- `ErrorResponse(status, code, message)` 하나로 통일. 인증 실패도 같은 모양으로 직렬화
- `@MessageExceptionHandler` 로 STOMP 예외를 `/user/queue/errors` 에 내려준다
- `@Payload` 전부에 `@Valid`
- 좌표 DTO 를 `Integer` + `@NotNull` + `0~23` 범위로
- `CustomException` 이 `super(message)` 를 부르게 해서 `getMessage()` 가 null 이 아니게
- 거절 로그를 DEBUG 로 내리고 판 밖 좌표만 WARN 유지
- `rankings?limit` 하한 보호
- `NOT_FOUND_USER` → `USER_NOT_FOUND`

### 왜 그렇게 고쳤는가

`/error` 허용과 예외 핸들러 추가는 **둘 다** 했다. 어느 하나만으로도 이번 증상은 사라지지만,
핸들러만 추가하면 앞으로 새로 생기는 미처리 예외가 다시 401 이 되고,
`/error` 만 열면 응답이 Spring 기본 형태로 나가 스키마가 또 갈라진다.
이중 안전망으로 두는 편이 맞다.

좌표를 `int` 대신 `Integer` 로 바꾼 이유는 **"필드 누락"과 "0번 지점"을 구분해야** 하기 때문이다.
범위 검증만 추가하면 0 은 유효한 값이라 누락이 계속 통과한다.

거절 로그를 전부 DEBUG 로 내리지 않고 판 밖 좌표만 WARN 으로 남긴 이유는,
DTO 검증을 통과할 수 없는 값이 들어왔다는 것은 클라이언트를 우회한 흔적이기 때문이다.
상대 차례에 누르거나 이미 찬 자리를 누르는 것은 평범한 오터치라 운영자가 볼 일이 없다.

### 기대 효과

- 잘못된 요청 때문에 로그아웃되지 않는다
- 클라이언트가 실패를 한 가지 형태로만 처리하면 된다
- 방장 전용 동작을 눌렀을 때 이유가 화면에 뜬다
- 잘못된 페이로드가 합법적인 수로 처리되지 않는다
- 운영 로그에서 봐야 할 것이 오터치에 묻히지 않는다

| `to: -1` | 무반응 | `INVALID_REQUEST` |
| `to: 5` (정상) | 정상 | 정상 (`STATE_CHANGED`) |

함정이 하나 있었다. Spring 메시징은 웹 계층과 **동명의 다른 클래스**
`org.springframework.messaging.handler.annotation.support.MethodArgumentNotValidException`
를 던진다. 처음에 웹 쪽을 import 해서 핸들러가 조용히 안 잡혔고,
검증은 막고 있는데 에러만 전달되지 않는 상태였다. 실측하지 않았으면 못 찾았을 것이다.
