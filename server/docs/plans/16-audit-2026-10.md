## 0. 한 줄 요약

**레이팅이 제로섬이 아니다.** 주석과 테스트는 제로섬이라고 말하는데,
K 계수가 플레이어마다 다르게 적용되므로 판마다 총합이 늘어난다.
Elo 로 바꾼 이유가 "기존 방식은 판마다 총합이 +10 씩 늘어 점수가 실력이 아니라 판수를 나타냈다"
는 것이었는데, 같은 성질이 다른 경로로 남아 있다.

## 1. P1

### P1-1. Elo 가 제로섬이 아니다 (실측 — 계산)

`Rating.delta` 는 K 를 **그 사람의 판수**로 고른다.

```java
// Rating.java:27
int k = myGamesPlayed < PLACEMENT_GAMES ? K_PLACEMENT : K_DEFAULT;   // 48 또는 32
```

`MatchResultService` 는 양쪽의 변동을 각자 계산한다.

```java
// MatchResultService.java:48-49
blackDelta = RatingPolicy.applyFactor(rawDelta(black, white, winner), factor);
whiteDelta = RatingPolicy.applyFactor(rawDelta(white, black, winner), factor);
```

`rawDelta` 안에서 `me.gamesPlayed()` 를 쓰므로 **두 사람의 K 가 다를 수 있다.**

| | MMR | 판수 | K | 변동 |
| --- | --- | --- | --- | --- |
| 신규 (승) | 1000 | 0 | 48 | **+24** |
| 고참 (패) | 1000 | 15 | 32 | **−16** |
| | | | | **합계 +8** |

`Rating` 클래스 주석은 이렇게 적혀 있다.

> 제로섬이라 한쪽이 얻는 만큼 상대가 잃고 전체 합이 보존됨

보존되지 않는다. 배치 중인 사람이 고참을 이길 때마다 사다리 전체에 점수가 주입된다.

**테스트가 이것을 잡지 못하는 이유**

`MatchResultServiceTest.원장에_변동값이_남는다` 가 합이 0 인지 확인한다.

```java
// MatchResultServiceTest.java:91
assertThat(match.getBlackMmrDelta() + match.getWhiteMmrDelta()).isZero();
```

그런데 `setUp` 이 두 사용자를 **둘 다 새로** 만들어 K 가 같다.
판수가 다른 조합을 넣는 케이스가 없어서 통과한다.

`applyFloor`(하한 100) 도 같은 성질의 누수다. 하한에 닿은 패자는 잃지 않는데 승자는 얻는다.

### P1-2. 정산 DB 트랜잭션이 방 락 안에서 돈다

`settle` 은 `rooms.mutate` 가 잡은 **방 단위 `synchronized` 블록 안**에서 불린다.

```java
// GameService.java:238-243
private void settle(Room room, MorrisGame game, Outcome outcome) {
    matchResultService.record(...);   // @Transactional — 쿼리 1 + UPDATE 2 + INSERT 1
    metrics.gameFinished(outcome.reason());
}
```

호출 경로 네 개가 모두 `mutate` 안이다 — 착수(`applyMove`), 이탈(`exit`),
유휴 정리(`settleAbandoned`).

**무엇을 야기하는가**

- 정산이 끝날 때까지 그 방의 모든 STOMP 프레임이 막힌다
- DB 가 느려지면 방이 그대로 멈춘다. 커넥션을 기다리는 동안 모니터를 쥐고 있다
- 데드락은 없다(락 획득 순서가 한 방향) 지만 지연이 전파된다

규칙 판정은 메모리 연산이라 락이 짧아야 하는데, I/O 가 그 안에 들어가 있다.
정산을 락 밖으로 빼려면 `mutate` 가 "정산할 결과" 를 돌려주고
호출자가 락을 놓은 뒤 기록하는 형태여야 한다.

### P1-3. 서버가 보내는 `endReason` 을 화면이 버린다

서버는 종료 사유를 계산해 모든 종료 이벤트에 싣는다 (`GameStateResponse.java:29`).
프론트에서 이 값이 쓰이는 곳은 두 군데뿐이다.

```
web/src/lib/types.ts:90      endReason: EndReason | null;   // 타입 선언
web/src/hooks/useGameState.ts:23  endReason: null,          // 초기값
```

**렌더링하는 곳이 없다.** `GameResultModal` 은 승/패/무만 보여준다.

그래서 3회 반복이나 50수 규칙으로 무승부가 나면 사용자는 **이유를 알 수 없다.**
갑자기 "무승부!" 가 뜨는 것은 사용자 입장에서 버그와 구분되지 않는다.

덤으로 프론트 `EndReason` 유니온에 **`ABANDONED` 가 빠져 있다.**
서버 enum 에는 7개인데 프론트는 6개다. 지금은 저장만 하므로 런타임 오류가 없지만,
`Record<EndReason, string>` 같은 매핑을 만드는 순간 방치 종료가 조용히 `undefined` 가 된다.

## 2. P2

### P2-1. 없는 URL 이 404 가 아니라 500 이 되고 ERROR 로그를 남긴다 (실측)

`CustomExceptionHandler` 가 `Exception` 전체를 받아 500 으로 바꾼다.

```java
// CustomExceptionHandler.java:43-46
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(Exception exception) {
    log.error("처리하지 못한 예외", exception);
    return ResponseEntity.internalServerError()...
}
```

관측성 작업 중 실제로 재현했다. 인가에서 허용된 경로인데 핸들러가 없으면
`NoResourceFoundException` 이 여기로 와서 500 + 스택트레이스가 된다.

```
ERROR c.n.c.e.CustomExceptionHandler - 처리하지 못한 예외
org.springframework.web.servlet.resource.NoResourceFoundException:
    No static resource actuator/prometheus.
```

`denyAll` 기본값 덕분에 대부분의 미지의 경로는 401 로 먼저 막혀 노출이 좁다.
그래도 ERROR 는 "사람이 개입해야 하는 것" 이라는 [10](10-logging-and-observability.md) 2절 기준과 어긋난다.
`NoResourceFoundException` / `NoHandlerFoundException` 은 404 로 내리고 로그를 낮춰야 한다.

### P2-2. 방 상세가 멤버 검사 없이 열려 있다

소켓 쪽은 남의 방 토픽 구독을 막아 뒀다.

```java
// ClientFrameGuard.java:90-92
if (destination.startsWith(ROOM_TOPIC_PREFIX)) {
    return isMember(destination, actor.id()) ? message : denied(...);
}
```

그런데 REST 쪽에는 같은 검사가 없다.

```java
// RoomController.java:45-48
@GetMapping("/{roomId}")
public RoomDetailResponse findOne(@PathVariable long roomId) {
    return roomService.findDetail(roomId);   // 멤버 검사 없음
}
```

로비 목록은 방장만 노출하는데, 이 엔드포인트는 **참가자의 id 와 닉네임까지** 준다.
[14](14-audit-2026-09.md) P0-1 과 같은 모양이다 — 소켓 문은 잠갔는데 그 옆 REST 문이 열려 있다.

피해는 작다(닉네임 노출). 다만 방 번호가 1부터 순증하므로 열거가 쉽다.

### P2-3. 무승부 제안에 제한이 없다

```java
// MorrisGame.java:165-168
private MoveResult offerDraw(Stone actor) {
    drawOfferedBy = actor;
    return new MoveResult.DrawOffered();
}
```

턴 검사도, 중복 검사도, 횟수 제한도 없다.
프론트는 `DRAW_OFFERED` 를 받을 때마다 모달을 띄운다(`Game/index.tsx:180-185`).

**상대에게 모달을 무한히 띄울 수 있다.** 판을 망치지는 않지만 괴롭힘 수단이다.
한 판에 N 회로 제한하거나, 거절당한 뒤 일정 수 동안 다시 못 내게 하는 쪽이 맞다.

작은 불일치 하나 더 — 주석은 "상대가 수를 두면 자동으로 소멸함" 이라고 하는데,
`remove` 는 `endTurn` 으로 바로 가므로 제거로는 제안이 지워지지 않는다
(`afterStoneLanded` 만 `drawOfferedBy = null` 을 한다).

### P2-4. 즉시 기권이 배치 판수를 채운다

레이팅은 `MIN_RATED_MOVES`(10수) 미만이면 움직이지 않는다. 그런데 전적은 남는다.

```java
// MatchResultService.java:61-62
black.applyMatchResult(blackDelta, outcomeOf(black, winner));   // delta 0 이어도 승패는 증가
white.applyMatchResult(whiteDelta, outcomeOf(white, winner));
```

`gamesPlayed` 가 늘면 `Tier.of` 의 배치 조건을 넘고, K 도 48 → 32 로 내려간다.
**붙자마자 기권을 10번 반복하면 한 판도 제대로 두지 않고 배치가 끝난다.**

비로그인 계정이 낀 판은 아예 기록하지 않아 이 경로가 막혀 있지만,
회원끼리는 그대로 열려 있다. P1-1 과 겹치면 K 를 의도적으로 조절하는 데 쓸 수 있다.

### P2-5. 유휴 정리에 경합 창이 있다

```java
// GameService.java:192-198
List<Long> idle = rooms.findIdle(Instant.now().minus(idleTimeout));
for (long roomId : idle) {
    settleAbandoned(roomId).ifPresent(broadcasts::add);
    rooms.remove(roomId);          // 락 밖. 그 사이에 들어온 사람이 있어도 지운다
}
```

`findIdle` 로 목록을 뜬 뒤 `remove` 까지 사이에 누군가 입장하면,
입장은 201 을 받았는데 방이 사라진다. 프론트는 "사라진 방" 을 띄운다.
확률은 낮다(30분 유휴 직후의 수 ms) 지만 구조적으로 열려 있다.

### P2-6. `AuthGate` 가 판정 전에 children 을 그린다

```java
// web/src/components/AuthGate.tsx
const { isLoading, isError } = useQuery(QUERY.CURRENT_USER);
useEffect(() => { if (!isLoading && isError) return navigate('/'); }, [...]);
return <>{children}</>;      // 로딩 중에도, 에러일 때도 일단 그린다
```

게임 화면이 인증 결과를 알기 전에 마운트되어 소켓을 먼저 연다.
토큰이 없거나 만료면 서버가 연결을 거절하고, 리다이렉트 전에 에러 모달이 한 번 번쩍인다.
서버가 막으므로 보안 문제는 아니고 화면 문제다.

### P2-7. 결과 모달이 무승부로 보일 수 있다

```jsx
// web/src/pages/Game/index.tsx:293-299
gameState.winnerId === currentUser?.userId ? 'WIN'
  : gameState.loserId === currentUser?.userId ? 'LOSS' : 'DRAW'
```

`currentUser` 가 아직 없으면 두 비교가 모두 거짓이라 **무승부로 떨어진다.**
P2-6 때문에 게임 화면이 프로필보다 먼저 뜰 수 있어 닿을 수 있는 경로다.
`currentUser` 가 없으면 모달을 띄우지 않는 쪽이 안전하다.

### P2-8. 레이트 리밋이 고정 창이라 경계에서 두 배가 통과한다

`VisitorIssueLimiter` 는 1시간 고정 창이다.
59분 59초에 10건, 1시간 00분 01초에 10건 → **2초 안에 20건**이 통과한다.

의도한 한도의 두 배까지는 구조적으로 열려 있다. 이 규모에서 피해는 작고,
[ADR-13](07-architecture-decision.md) 대로 Redis 로 옮길 때 슬라이딩 창으로 바꾸면 된다.
지금은 "알고 있는 한계" 로 남긴다.

### P2-9. 컨벤션 — 클래스 레벨 `readOnly` 누락

[java-conventions](../../.claude/rules/java-conventions.md) 는
"서비스 클래스에 `@Transactional(readOnly = true)`, 쓰기 메서드에만 `@Transactional`" 로 정하고 있다.

| 클래스 | 현재 |
| --- | --- |
| `UserService` | ✅ 클래스 `readOnly` |
| `RoomService` | ✅ 클래스 `readOnly` |
| `MatchResultService` | ❌ 메서드 `@Transactional` 만 |
| `VisitorService` | ❌ 메서드 `@Transactional` 만 |
| `CustomOAuth2UserService` | ❌ 메서드 `@Transactional` 만 |

세 개 모두 쓰기 메서드만 가진 클래스라 동작 차이는 없다. 규칙과 코드가 어긋난 것이 문제다.

### P2-10. `Mills.containing` 이 내부 배열을 그대로 반환한다

```java
// Mills.java:40
public static int[][] containing(int point) {
    return BY_POINT[point];      // 복사 없음
}
```

`all()` 은 `clone()` 을 하지만 얕은 복사라 내부 `int[]` 는 공유된다.
호출자가 원소를 고치면 **모든 게임의 밀 정의가 바뀐다.**
지금 호출자는 `Board` 와 테스트뿐이라 사고는 없다. 불변식을 코드로 막아두지 않은 상태다.

## 6. UI 조사 (실측)

서버와 프론트를 띄우고 헤드리스 브라우저로 **게스트 둘이 한 판을 끝까지 두며** 단계마다 화면을 찍었다.
방 생성 → 입장 → 선공 설정 → 착수 → 3연속 → 제거 → 상대 차례 착수 → 기권 → 결과 → 랭킹 → 모바일.

### 6-1. 서버·코드엔 있는데 화면에 없는 것
