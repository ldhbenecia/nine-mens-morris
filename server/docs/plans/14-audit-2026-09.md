# 2차 전수조사 (2026-09-13)

1차 조사([01-code-audit.md](01-code-audit.md))의 P0 13건을 고치고, 규칙 엔진·프로토콜·MMR 을 새로 올린 뒤의 상태를 다시 훑었다.
1차와 다른 점은 **실제로 서버를 띄워 놓고 소켓과 REST 를 직접 찔러서 확인**했다는 것이다.
아래 "실측" 표시가 붙은 항목은 추측이 아니라 재현한 것이다.

조사 범위는 네 갈래로 나눴다.

| 갈래 | 결과 |

## 0. 한 줄 요약

**가장 심각한 것은 "게임이 끝나는 경로가 네 개인데 그중 세 개가 결과를 기록하지 않는다"는 점이다.**

| 게임 종료 경로 | 정산(기권·MMR·matches) | 방 정리 |
| --- | --- | --- |
| 수를 둬서 승부가 남 | O | 방이 남음 (P1-4) |
| 소켓이 끊김 + 유예 만료 | O (단, 조건부로 아예 안 돌 수 있음 — P0-2) | **X** |
| REST 로 나가기 | **X** | O |
| 30분 유휴 정리 | **X** | O |

이 표 하나가 "진행 중인데 DB 에 아무것도 없다"던 증상의 정체다.
네 경로가 공유할 **`finishRoom(room, outcome)` 단일 종료 루틴**이 없는 것이 근본 원인이다.

## 1. P0 — 지금 당장 망가져 있는 것

### P0-1. REST 로 나가면 기권 없이 판이 사라진다 (실측)

`RoomService.leave` 에 진행 중 검사가 없다.
게스트면 `leaveGuest()` 가 `game = null` 로 판을 지우고, 방장이면 `rooms.remove()` 가 방을 지운다.
둘 다 `settle()` 을 타지 않는다.

소켓이 끊기는 경로(`handleDisconnect`)는 기권 처리를 하도록 일부러 만들어 놨는데,
그 바로 옆에 REST 문이 열려 있었다.

**실측 재현**

```
게임 PLAYING 상태 → 게스트가 DELETE /api/v1/rooms/{id}/players/me
→ 204
→ 방: playing:false, guestId:null
→ 호스트가 받은 이벤트: PLAYER_LEFT 뿐
→ matches 건수: 2 → 2 (변화 없음)
→ 승패·MMR: 변화 없음
```

즉 **지고 있으면 나가기를 누르는 쪽이 이득이다.** 1차 조사에서 막았다고 생각한 어뷰징이
다른 문에서 그대로 살아 있었다.

### P0-2. 다른 탭이 열려 있으면 끊김 정산이 아예 예약되지 않는다 (실측)

```java
if (sessions.hasActiveSession(userId)) {
    return;                 // 예약조차 하지 않음
}
```

`hasActiveSession` 은 **사용자 단위**라 "같은 방에 다시 붙었다"와 "무관한 탭이 하나 떠 있다"를
구분하지 못한다. 로비를 탭 A 에 띄워 두고 탭 B 에서 게임하다 탭 B 만 닫으면 정산이 영구히 안 돈다.

턴 제한 시간이 코드에 전혀 없으므로 상대는 그냥 멈춘 판을 보게 되고,
30분 뒤 유휴 정리가 기록 없이 방을 지운다(P0-3).

**실측 재현**

```
게스트가 탭 2개(게임 + 여분) → 게임 탭만 닫고 13초 대기
→ 호스트가 받은 이벤트: 없음
→ 방: playing:true, guestId 그대로
→ 랭킹: 변화 없음
```

### P0-3. 유휴 정리가 진행 중인 방을 정산 없이 지운다

`purgeIdleRooms` 는 `lastActivityAt` 만 보고 `rooms::remove` 를 호출한다.
`isPlaying()` 검사도, `GameService` 통보도 없다. 로그는 건수만 남기므로
"내 판이 사라졌다"는 제보가 왔을 때 운영자가 볼 근거가 없다.

`mutate` 는 방 단위 락을 잡는데 정리는 안 잡는다. 30분 임계값 + `touch()` 덕에
실제 충돌 창은 아주 좁지만, `lastActivityAt` 이 `volatile` 도 아니라서 낡은 값을 읽는 게 허용된다.

## 3. P2 — 정리해야 할 것

**데드코드 (사용처 0건, grep 확인)**

- 서버: `MorrisResponse`, `MorrisResponseCode` 파일 2개 통째로. 용어집이 금지한 `withdraw`·`tie`·`3행/3열` 표현을 담고 있는 유일한 곳이기도 하다
- 서버: `UserRepository.findByNickname`, `MatchRepository.findRecentByUserId`, `User.changeProfile`, `RoomService.find(long)`, `RoomRegistry.size()`, `RoomEvent.message`, `RatingPolicy.isRated` 의 `guestInvolved` 파라미터
- 프론트: `lib/constants.ts` 의 `TRIPLE`·`NEIGHBOR`(규칙이 서버로 갔으므로), `sounds.ts` 의 `errorSound`, 아이콘 3개, `useGameState` 가 반환하지만 아무도 쓰지 않는 6개, `GameResultModal.score`, `Status.visible`, `jotai`·`sockjs-client` 의존성

**일관성**

- 에러 응답 스키마가 세 종류: `{status,name,message}` / `{code,message}` / Spring 기본 `ProblemDetail`
- `GameStateResponse` 가 보드 배열을 `cells` 로 부른다 (용어집은 `point`)
- `RoomSummaryResponse` 만 `hostRating`·`rating`, 나머지는 전부 `mmr`
- `ErrorCode` 가 `NOT_FOUND_USER` 와 `ROOM_NOT_FOUND` 를 섞어 쓴다
- `Room.finish()` 는 `touch()` 만 하는데 이름은 상태 전이를 약속한다. `mutate` 가 이미 `touch()` 를 부르므로 이중 호출

**정확성·운영**

- 미등급 게임(10수 미만)도 승패 카운터를 올린다 → 즉시 기권으로 배치 10판을 소모해 K 를 48→32 로 낮추거나 표시용 승수를 부풀릴 수 있다
- `/users/me` 의 순위(`count(mmr>)+1`)와 `/rankings` 의 순위(리스트 인덱스)가 동점에서 불일치. 정렬에 타이브레이커 컬럼도 없다
- `nickname` 에 unique 제약이 없는데 `findByNickname` 은 `Optional` 을 반환한다
- `record` 가 멱등하지 않다. 지금 한 번만 불리는 건 서로 무관한 두 파일의 불변식에 기대고 있을 뿐이다
- `TaskScheduler` 풀 크기가 기본값 1 이다. 유휴 정리와 모든 재접속 유예 작업이 한 스레드를 공유한다
- 테스트 설정에만 타임존 속성이 빠져 있다. 24시간 윈도 쿼리가 운영과 다른 설정으로 돌고 있다
- `Flyway` 없음 + 운영은 `ddl-auto: validate`, 테스트는 `create` → 운영 DDL 이 한 번도 검증되지 않는다
- `graceful shutdown` 미설정 → 배포할 때 진행 중인 판이 그냥 죽는다

**테스트 공백 (가장 중요)**

`MatchResultService.record` 가 **등급 게임(10수 이상)으로 한 번도 실행된 적이 없다.**
E2E 와 단위 테스트 둘 다 1수 후 기권으로 끝나서 `MIN_RATED_MOVES = 10` 에 걸려 `isRated == false` 가 된다.
따라서 아래가 전부 미검증이다.

- 제로섬 MMR 쓰기가 한 트랜잭션으로 커밋되는지 (이 클래스의 존재 이유)
- `User.applyMatchResult` 의 `FLOOR` 클램프와 `peakMmr` 갱신이 실제로 영속화되는지
- `rated = true` 가 써지는지
- `repeatOpponentFactor` 의 24시간 윈도 쿼리가 MySQL 에서 맞게 도는지

`morris-storage` 와 `morris-support` 에는 `src/test` 디렉터리 자체가 없다.

## 4. 정상 확인된 것

조사에서 "없음"이 누락이 아니라 근거임을 남기기 위해 적는다.

**규칙 엔진** — 턴·단계·범위·점유·소유권·인접성·밀 보호·전부-밀 예외가 모두 서버에서 강제된다.
`RejectReason` 14개가 `default` 없는 `switch` 로 전부 매핑돼 새 값 추가 시 컴파일 오류가 난다.
인접 그래프는 32간선 완전 대칭, 24지점이 각각 정확히 2개 밀에 속함을 프로그램으로 검증.
`endTurn` 이 **다음** 플레이어를 판정하는 것이 올바른 나인멘스모리스 의미이고, `isDefeated` 는 배치 단계를 면제한다.

**행위자 식별** — 요청 DTO 어디에도 사용자 식별자가 없고 모든 `RoomCommand` 첫 인자가 `actorId`,
채워지는 곳은 `Principal` 뿐. `AuthenticatedUser.from` 은 익명에 null 을 돌려주고 두 호출부 모두 닫힘 실패한다.

**동시성(쓰기)** — `mutate` 의 방 단위 락은 실제로 충분하다. 같은 방 id 의 `Room` 인스턴스는 교체되지 않으므로
두 탭에서 동시에 보낸 수가 같은 모니터에서 직렬화된다. 동시 끊김에서도 **경기 기록은 정확히 한 번만** 남는다.

**전송 보안** — `/topic` 직접 `SEND` 위조는 연결 종료(1002)로 차단되고 피해자에게 전달되지 않는다(실측).
CORS·CSWSH 오리진이 설정에서 오고 `*` 가 없다. JWT 는 HS256 고정이라 `alg:none`·RSA→HMAC 혼동이 불가능하다.
`anyRequest().denyAll()` 기본 거부, actuator 는 health 만 열려 있고 `show-details` 는 never.

**모듈 경계** — `morris-core` 의 `dependencies {}` 가 실제로 비어 있고 Spring/jakarta import 가 0건이다.
`@OneToMany`/`@OneToOne`/`@ManyToMany` 가 어디에도 없다. `open-in-view: false`.

**로깅 모범 사례** — `JwtProvider` 의 만료 토큰 DEBUG 처리, `MatchResultService` 의 한 줄 경기 기록
(양쪽 id·부호 있는 델타·승자·사유·수 수·등급 여부)은 분쟁 재구성에 필요한 걸 다 담고 있다.

## 5. 작업 순서

네 경로가 공유할 종료 루틴을 먼저 만들고, 거기에 맞춰 나머지를 붙인다.

1. **P0-1** — `leave` 가 진행 중이면 기권 경로를 타게 한다 (가장 작은 diff, 활성 어뷰징을 닫음)
2. **P0-2** — 세션 추적을 방 단위로 바꾼다
3. **P1-4 + P0-3** — 정산 후 방 정리, 유휴 정리도 정산하게. 1~3 은 사실 같은 개념 하나(`finishRoom`)
4. **P1-2 + P1-3** — `/error` 디스패치 허용 + 검증/STOMP 예외 핸들러. 에러 스키마 하나로 통일
5. **P1-1** — `SUBSCRIBE` 인가 (CONNECT 시 인증 요구 + 방 멤버십 검사)
6. **P1-5 + P1-6** — `snapshot` 을 락 안으로, `SessionTracker` 원자성. 둘 다 두 줄짜리
7. **F-P0-1~3** — 프론트 404·종료 화면·`playing` 기준 분기
8. **P1-9 + P1-10** — 인덱스, 트랜잭션
9. 등급 게임 정산 Testcontainers 테스트 (위 변경들의 회귀 방지망)
10. 데드코드 제거, 용어·스키마 일관성 (단독 커밋)
