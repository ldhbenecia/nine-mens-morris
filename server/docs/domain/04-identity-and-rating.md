# 04. 신원과 레이팅

## 두 종류의 사용자

| | 카카오 회원 | 비로그인 사용자 (visitor) |
| --- | --- | --- |
| 화면 표기 | 닉네임 · 티어 · MMR | 닉네임 · "게스트" |
| `users.provider` | `KAKAO` | `VISITOR` |
| `users.provider_id` | 카카오 회원번호 | null |
| 닉네임 | 카카오 프로필(20자로 자름). 동의 안 했으면 회원번호로 만듦. 로그인마다 갱신 | 서버가 지음 (`조용한물맷돌4821` 형태, 유일성 보장 아님) |
| 토큰 역할 | `ROLE_USER` | `ROLE_VISITOR` |
| 토큰 유효기간 | 1시간 (`ACCESS_TOKEN_EXPIRATION`) | 7일 (`VISITOR_TOKEN_EXPIRATION`) |
| 할 수 있는 것 | 전부 | 전부 (방 생성·입장·대국) |
| 전적·MMR | 반영 | **반영하지 않음.** visitor 가 낀 판은 기록 자체를 하지 않음 |
| 랭킹·내 등수 | 나옴 | 나오지 않음 |
| 정리 | — | 만든 지 30일 지난 행을 매일 04:00 삭제 (`IdleVisitorPurger`) |

- visitor 도 **익명이 아니라 서버가 발급한 신원**이다. 신원이 없으면 방 소유권도 턴 검증도 소켓 인가도 걸 곳이 없다
- visitor 토큰이 긴 이유: 토큰을 잃으면 그 신원으로 돌아올 방법이 없어 짧으면 게임 도중 끊긴다. 탈취돼도 잃을 전적·레이팅이 없다
- visitor 와 카카오 계정은 **연결되지 않는다.** visitor 로 놀다가 로그인하면 새 신원이다
- 기본키 `user_id` 는 서비스가 발급한다. 카카오 회원번호를 기본키로 쓰면 회원번호가 없는 visitor 를 만들 수 없다
- 같은 카카오 계정이 두 행이 되는 것은 `uk_users_provider (provider, provider_id)` 가 막는다. visitor 는 provider_id 가 null 이라 이 제약에 걸리지 않는다

## 로그인 흐름

### 카카오

```
브라우저 ── /oauth2/authorization/kakao ──▶ 서버: state 생성, 인가 요청을 Redis 에 5분 저장 ──▶ 카카오 로그인
카카오 ── /api/oauth2/kakao?code&state ──▶ 서버(어느 파드든): Redis 에서 state 로 인가 요청을 꺼내며 지움
                                          → 토큰 교환 → 사용자 조회/생성(CustomOAuth2UserService)
                                          → JWT 발급 → {프론트}/auth/callback#token=<JWT> 로 리다이렉트
프론트 AuthCallback: 프래그먼트에서 토큰을 읽어 localStorage 에 저장, 주소창에서 지움
```

- 인가 요청을 **세션이 아니라 Redis** 에 두는 이유: 서버가 여러 대면 로그인 시작과 콜백을 다른 파드가 받는다 (`RedisOAuth2AuthorizationRequestRepository`)
- 토큰을 **쿼리가 아니라 프래그먼트**로 주는 이유: 프래그먼트는 서버로 전송되지 않아 액세스 로그·Referer 에 남지 않는다
- JWT subject 는 카카오 회원번호가 아니라 내부 `user_id`

### 비로그인

`POST /api/v1/auth/visitors` → `{ accessToken }`. IP 당 **1분 슬라이딩 창에 5건**까지 (`VisitorIssueLimiter`, Redis ZSET + Lua).
서버가 여러 대여도 한도는 하나로 센다. 메모리에 두면 서버가 8대일 때 한도가 8배가 된다.

### 토큰 보관 (프론트)

- `localStorage` (`web/src/lib/auth.ts`). 쿠키가 아닌 이유: 프론트(GitHub Pages)와 서버가 cross-site 라 쿠키를 쓰려면 `SameSite=None` 이 필요하고, 그건 CSRF 방어를 버리는 것이다
- 대신 XSS 가 나면 토큰을 읽힌다. 유효기간을 짧게 두는 것으로 감수한다
- 다른 탭에서 로그인·로그아웃·게스트 시작으로 토큰이 바뀌면 이 탭을 새로고침한다. 열어 둔 소켓과 다시 받은 내 정보의 신원이 갈리면 내 돌을 상대 돌로 본다
- 401 을 받으면 토큰을 지운다. 로그아웃은 서버가 할 일이 없고 클라이언트가 토큰을 버리는 것으로 끝난다

## 레이팅 (MMR)

Elo 기반. 계산은 `morris-core` 의 `Rating`, 어뷰징 대책은 `RatingPolicy`, 반영은 `MatchResultService`.

| 값 | |
| --- | --- |
| 시작 MMR | 1000 (SILVER 구간) |
| 하한 | 100. 잃는 쪽이 하한 아래로 내려갈 만큼은 깎고, 그만큼 얻는 쪽도 덜 얻음(제로섬 유지) |
| K | 배치 중(10판 미만) 48, 이후 32. **두 사람 K 의 평균**을 씀 |
| 변동 | 한 판에 하나만 계산하고 상대는 부호만 뒤집음. 따로 계산하면 판마다 총합이 늘어남 |
| 무승부 | 점수 0.5 로 계산. 등급 차가 크면 무승부에도 MMR 이 움직임 |
| `peak_mmr` | 최고 기록. 엔티티가 갱신을 보장 |

### 정산 규칙 (`MatchResultService.record`)

판이 끝날 때마다 **락을 푼 뒤** 한 트랜잭션으로 반영한다. 승자 갱신·패자 갱신·전적 저장이 따로 커밋되면 점수 총합이 어긋난다.

| 상황 | `matches` 원장 | 승패 수 | MMR |
| --- | --- | --- | --- |
| visitor 가 한 명이라도 낌 | **기록 안 함** | — | — |
| 10수 미만으로 끝남 (`MIN_RATED_MOVES`) | 기록 (`rated=false`) | 안 오름 | 변동 0 |
| 같은 두 사람이 24시간 안에 이미 6판 이상 | 기록 (`rated=false`) | 안 오름 | 변동 0 |
| 그 밖 | 기록 (`rated=true`) | 오름 | 변동 |

같은 상대와 24시간 안에 앞서 둔 판 수에 따른 감쇠 계수 (`RatingPolicy.repeatOpponentFactor`):

| 앞서 둔 판 | 0~1 | 2~3 | 4~5 | 6+ |
| --- | --- | --- | --- | --- |
| 계수 | 1.0 | 0.5 | 0.25 | 0 (랭크전 아님) |

- 10수 미만을 막는 이유: 붙자마자 기권을 반복해 상대 MMR 을 올려 주는 파밍
- 승패 수를 올리지 않는 이유: 오르면 즉시 기권·짜고 치는 반복으로 배치 판수를 채워 티어를 받음
- visitor 판을 아예 안 남기는 이유: visitor 는 무한히 만들 수 있어 전적만 남겨도 배치 판수를 공짜로 채울 수 있음
- 한 사람이 여러 방에서 두 판을 동시에 끝낼 수 있어 `users` 행을 **비관적 락**으로 읽는다. 항상 `user_id` 순으로 잠가 교착을 막는다
- 정산이 실패해도(DB 장애) 종료 알림은 나간다. 실패한 판은 `정산 실패` ERROR 로그에 결과 전체가 남고, 자동 재시도는 없다

### "랭크전" 표시 (`rated`)

방 목록·상세의 `rated` 는 **두 자리가 모두 회원**인지만 본다. 10수·반복 조건은 끝나 봐야 알 수 있어 화면에는 반영되지 않는다.
참가자가 없으면 방장 기준이다. visitor 가 들어오는 순간 일반전으로 바뀐다.

## 티어 (`Tier`)

배치 10판을 채우기 전에는 `UNRANKED`. 이후 MMR 구간:

| 티어 | MMR | 화면 |
| --- | --- | --- |
| BRONZE | ~ 899 | 브론즈 |
| SILVER | 900 ~ 1099 | 실버 |
| GOLD | 1100 ~ 1349 | 골드 |
| PLATINUM | 1350 ~ 1649 | 플래티넘 |
| DIAMOND | 1650 ~ 1999 | 다이아몬드 |
| MASTER | 2000 ~ | 마스터 |

구간 폭이 위로 갈수록 넓다(200/250/300/350). Elo 는 400점 차이가 기대 승률 10:1 이라 같은 폭이면 상위 등급이 실제보다 쉽게 나온다.
한글 표기는 프론트(`web/src/lib/tier.ts`)가 매핑한다.

## 랭킹과 내 등수

- 랭킹: 회원만, `mmr desc, user_id asc`. 동점은 같은 등수, 다음 사람은 인원수만큼 건너뜀(1, 2, 2, 4)
- 내 등수: 나보다 MMR 이 높은 회원 수 + 1. visitor 는 null
- 인덱스 `(provider, mmr desc)` 로 상위 N 명만 읽고 멈춘다. `<> VISITOR` 로 쓰면 범위가 둘로 갈라져 회원 전체를 정렬하므로 `IN (회원 제공자들)` 로 쓴다
