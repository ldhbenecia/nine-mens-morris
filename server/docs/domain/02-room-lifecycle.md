# 02. 방과 판의 생애

방(`Room`)은 두 사람의 자리와 설정을 갖고, 그 안에 판(`MorrisGame`)이 0개 또는 1개 있다.
방은 DB 가 아니라 **Redis 에만** 있다. 수명이 수십 분이라 DB 행으로 두면 고아 행이 쌓인다.
판이 끝나면 결과만 MySQL(`matches`, `users`)에 남는다.

## 상태

```
           생성
            │
            ▼
   ┌──── 대기 (참가자 없음) ◀──────────── 참가자 퇴장 (판이 진행 중이 아닐 때)
   │        │ 입장
   │        ▼
   │     모임 (두 명, 판 없음 · 또는 끝난 판이 남아 있음)
   │        │ 방장이 시작
   │        ▼
   │     진행 중 (PLAYING) ──── 수 · 제안 ────┐
   │        │ 승패/무승부 확정               │
   │        ▼                                │
   │     끝남 (FINISHED, 판이 남아 결과를 보여 줌) ◀┘
   │        │ 방장이 다시 시작하면 새 판
   │
   └── 방장 퇴장 · 유휴 정리 → 삭제
```

| 판단 | 메서드 | 뜻 |
| --- | --- | --- |
| 가득 찼나 | `Room.isFull()` | 참가자가 있음 |
| 진행 중인가 | `Room.isPlaying()` | 판이 있고 `PLAYING`. 끝난 판이 남아 있어도 false |
| 판이 있었나 | `Room.hasGame()` | 끝난 판 포함. 새로고침한 화면이 대기실을 띄울지 판을 띄울지 고르는 기준 |
| 이 사람이 방에 속하나 | `Room.contains(userId)` | 방장 또는 참가자 |

- **새 참가자가 들어오면 지난 판은 버린다** (`Room.join`). 같은 상대와 이어 두면 끝난 판 위에 새 판을 시작한다
- 참가자가 나가도 끝난 판은 남는다. 남은 방장이 새로고침해도 결과를 볼 수 있어야 한다
- 방장과 참가자는 흑백과 별개다. 흑백은 시작할 때 선공 방식으로 정한다 (`blackId`, `whiteId`)

## 단계별로 일어나는 일

"방 토픽" 은 `/topic/rooms/{roomId}`, "로비" 는 `/topic/lobby` 다. 로비 신호는 아래 [로비 신호](#로비-신호) 규칙에 따라 저장소가 낸다.

| 일 | 입구 | 서버가 하는 일 | 방 토픽 | 로비 |
| --- | --- | --- | --- | --- |
| 방 생성 | `POST /api/v1/rooms` | 번호 발급(`rooms:seq`), 저장 | — | ✓ |
| 입장 | `POST /api/v1/rooms/{id}/players` | 락 안에서 빈자리 확인 후 참가자 기록. 이미 참가·가득 참이면 거절 | `PLAYER_JOINED` (actorId) | ✓ |
| 선공 방식 변경 | STOMP `settings` | 방장만, 진행 중이 아닐 때만 (끝난 뒤 다음 판 전에도 가능) | `SETTINGS_CHANGED` (actorId) | ✓ |
| 시작 | STOMP `start` | 방장만, 두 명일 때만. 흑백 확정, 새 판, 시계 시작 | `STARTED` (판 상태) | ✓ (진행 중) |
| 착수 | STOMP `place`/`move`/`remove` | `MorrisGame.apply`. 판이 바뀌면 시계 재시작 | `STATE_CHANGED` 또는 `FINISHED` | 끝났을 때만 |
| 무승부 제안·거절 | STOMP `draw-offer`/`draw-decline` | 판은 그대로 | `DRAW_OFFERED`/`DRAW_DECLINED` (actorId) | — |
| 무승부 수락·기권 | STOMP `draw-accept`/`resign` | 판 종료, 정산 | `FINISHED` | ✓ |
| 거절된 수 | 위 STOMP 전부 | 판 그대로. **저장도 하지 않음** | — (요청자 개인 큐로 거절 사유) | — |
| 나가기 | `DELETE /api/v1/rooms/{id}/players/me` | 아래 [나가기·끊김](#나가기끊김) | `PLAYER_LEFT` 또는 `FINISHED` | ✓ |
| 연결 끊김 | 소켓 종료 + 10초 유예 | 아래 [나가기·끊김](#나가기끊김) | `PLAYER_LEFT` 또는 `OPPONENT_DISCONNECTED` | ✓ |
| 시간 초과 | 스케줄러 1초 | 차례인 쪽 패배, 정산 | `FINISHED` | ✓ |
| 유휴 정리 | 스케줄러 5분 | 30분 동안 변화 없는 방 삭제. 진행 중이면 `ABANDONED` 무승부로 정산 | 진행 중이었으면 `FINISHED` | ✓ |
| 재접속 복구 | STOMP `sync` | 락 없이 한 번 읽음. 방에 속하고 판이 있었을 때만 | — (요청자 개인 큐로 `SNAPSHOT`) | — |

## 나가기·끊김

같은 루틴(`GameService.exit`)을 탄다. 경로마다 따로 두면 정산을 빠뜨리기 쉽다.

| 판이 | 나간 사람 | 결과 |
| --- | --- | --- |
| 진행 중이 아님 | 참가자 | 대기 상태로 돌아감. `PLAYER_LEFT` |
| 진행 중이 아님 | 방장 | 방 삭제. `PLAYER_LEFT`. 남은 사람 화면은 방을 다시 읽다가 404 → "사라진 방" |
| 진행 중 | 누구든 | **나간 사람이 기권**한 것으로 정산. 나가기면 `FINISHED`, 끊김이면 `OPPONENT_DISCONNECTED`. 그 뒤 위와 같이 방 정리 |

지고 있을 때 나가거나 창을 닫으면 이득이 되지 않게, 진행 중 이탈은 반드시 기권으로 기록한다.

### 끊김 판정 — 10초 유예와 서버 전체 기준

새로고침·화면 이동만으로 방이 사라지면 안 된다.

1. 소켓이 끊기면(`SessionDisconnectEvent`) 그 세션이 보던 방마다 10초 뒤 확인을 예약한다
2. 10초 뒤, 그 사용자가 **어느 서버에든** 그 방 토픽을 구독한 세션이 하나라도 있으면 아무것도 하지 않는다 (`ClusterPresence.isWatching`)
3. 없으면 `handleDisconnect` → 위 표대로 처리

다른 서버로 다시 붙었을 수 있어 이 서버의 세션만 보고는 판단할 수 없다. 접속 여부는 Redis 에 서버 전체 기준으로 둔다([05](05-architecture.md)).

## 로비 신호

로비 화면은 목록 전체를 소켓으로 받지 않고, **"바뀌었다" 신호만 받아 REST 로 다시 읽는다.**
목록 전체를 흘리면 접속자 수만큼 같은 데이터가 반복 전송된다.

신호는 모든 변경이 지나는 `RedisRoomRegistry` 가 판단해 `LobbyChanged` 이벤트로 내고, `LobbyNotifier` 가 전송한다.

| 낸다 | 내지 않는다 |
| --- | --- |
| 방 생성, 방 삭제 | 착수처럼 판 안에서만 보이는 변화 |
| 로비에 보이는 값(`Room.LobbyView`: 인원·진행 여부·선공 방식)이 바뀜 | 거절된 수, 바뀐 게 없는 변경 |

로비에 새 값을 보이게 하려면 `LobbyView` 에 넣어야 신호가 나간다.

## revision — 이벤트 순서

서버 여러 대가 같은 방의 이벤트를 보내므로 **도착 순서가 뒤바뀔 수 있다.** 판 상태에는 방이 바뀔 때마다 오르는 `revision` 이 실리고,
클라이언트는 지금 들고 있는 것보다 **작은** revision 의 판을 버린다(`web/src/pages/Game/index.tsx`).

- 저장소가 **변경을 적용하기 전에** 올린다. 변경 안에서 만든 이벤트가 저장될 번호를 달고 나가야 "같은 번호 = 같은 판" 이 성립한다
- 바뀐 게 없는 변경(거절된 수 등)은 저장하지 않으므로 번호도 오르지 않는다
- 개인 큐로 가는 `SNAPSHOT` 과 방 토픽 이벤트가 섞여 와도 같은 규칙으로 걸러진다

## 프론트 화면 흐름 (`web/src/pages/Game/index.tsx`)

1. 방 상세(`GET /rooms/{id}`)로 방장·참가자·`hasGame` 을 읽어 대기실(`WaitingRoom`)과 판 화면 중 고른다
2. 소켓 연결 → 방 토픽, `/user/queue/errors`, `/user/queue/sync` 구독 → `sync` 전송
3. 이벤트마다 판 상태 교체(revision 가드), 효과음, 마지막 수 표시, 이동·제거 연출
4. `FINISHED` 면 결과 창. 점수가 반영된 뒤에 종료가 오므로 받자마자 내 정보를 다시 읽으면 바뀐 MMR 이 보인다
5. `ROOM_NOT_FOUND` 를 받으면 "방이 사라졌다" 창을 띄우고 내보낸다
6. 연결은 `ManagedSocket`(`web/src/lib/socket.ts`)이 관리한다. 붙을 때마다(재접속·서버 이동 포함) 구독과 `sync` 를 다시 한다
   - 서버가 `RECONNECT` 를 보내면 새 연결을 먼저 붙이고 옛 연결을 닫는다. 화면에는 아무것도 보이지 않는다
   - 예고 없이 끊기면 0.5초부터 두 배씩 5초까지 다시 붙고, **3초 넘게 못 붙을 때만** 끊김 창을 띄운다
   - 연결이 없는 동안 둔 수는 "다시 잇는 중" 안내를 띄운다

## 서버 교체(배포) 중 연결 이동

소켓은 특정 서버와 맺은 연결이라 서버가 내려가면 끊길 수밖에 없다. 배포처럼 **계획된 교체**에서는 끊기기 전에 옮긴다.

```
쿠버네티스: 새 파드 준비 → 옛 파드를 엔드포인트에서 뺌(preStop 5초) → SIGTERM
옛 서버:   readiness DOWN → 자기 세션들에게 /topic/system 으로 RECONNECT → 세션이 다 떠날 때까지(최대 10초) 대기 → 종료
브라우저:  새 연결 열기(새 파드로 감) → 방 토픽·개인 큐 구독 → sync → 옛 연결 닫기
```

- 옮기는 사이 옛 연결로 보낸 수도 옛 서버가 Redis 에 반영하므로 입력이 비는 구간이 없다
- 옛 연결을 닫아 생기는 이탈 판정은, 새 연결이 이미 접속 기록에 있어 기권으로 처리되지 않는다
- 1초 남짓 두 연결이 같은 이벤트를 받는다. revision 이 같아 판은 한 번만 바뀐다
- 서버 쪽은 `SocketDrainer`, 결정 경위는 ADR-18
